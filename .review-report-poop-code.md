## Decisions I made

1. **Dead Letter's `can_seal` is not stored on the drop.** The contract fixes `Dropping`'s fields;
   the trigger reads `player.loadout` for `kind == Hantavirus && evolved`, which is the flag the old
   tag copied into `Infection::can_seal`. An evolution is permanent, so the two cannot disagree.
2. **No line-of-sight test on the trigger**, per the contract's explicit eligibility list
   ("within radius + enemy radius", nothing about walls). The *drop* is the only wall-aware step:
   a drop that would land inside masonry lands under the rat.
3. **rng.** Nothing in the drop, the aging, the expiry, the eviction or the boss check draws rng.
   `vfx::emit_virus_tag` is called at the infection moment, so the per-infection draw count and
   order are the old tag's (the old tag also drew it once per tag).
4. **Boss order.** Enemies are tried before the boss for a given drop (the old tag ranked enemies
   before boss points), and a boss already mid-chain is skipped, as before.
5. **`VIRUS_RANGE` kept** as documented history with `#[allow(dead_code)]` rather than deleted, so
   the wave-3 design doc's reference still resolves.
6. **Library plate**: I chose the small version — the rat turns on the spot and the three targets
   walk slowly *in* — rather than teaching the plate machinery a rat lap. Consequence to know
   about: a body stepping in a drop the rat just left is inside the `< 26 px` radius where the
   renderer hides damage digits, so the card shows the magenta tag flash, the pips and the jump but
   no hit numbers. The drop clock on the card is the card's (`DROP_EVERY`); the drop, its arm, the
   trigger and the chain are the weapon's own.
7. **Bot**: `src/game/bot.rs` has no Hantavirus *rule*, only a comment and the upgrade-value tier
   (`weapon_tier`, `:2861–2864`: "needs a pack around the host"). The tier and its reasoning still
   hold (a chain needs neighbours to jump to), so I left the file untouched.

## Unverified / likeliest not to compile

- **`src/game/art_droppings.rs` does not exist in my worktree** (the art worker owns it). My
  `pub mod art_droppings;` (`src/game/mod.rs:54`) and the call at `src/game/world.rs:2396` only
  compile once that file is merged. I call
  `art_droppings::draw_dropping(pb, d, cam, self.elapsed)` with `d: &Dropping`, `cam: Vec2`,
  `elapsed: f32`, exactly the contract's signature.
- `DroppingScratch` (`weapons_wave3a.rs:479`) is a `SystemParam` of four `Local`s; `droppings_system`
  therefore has 13 parameters. If bevy objects to the derive or the borrow of
  `scratch.order` vs `scratch.claimed` inside one loop, splitting `claimed` into its own `Local`
  parameter is the one-line fix (14 params, still under the cap).
- `droppings.get(entity)` on `Query<(Entity, &SpawnId, &mut Dropping)>` is used read-only — that is
  the pattern `acid_rain_system` already uses, so it should be fine.
- `Vec2::from_angle` and `Vec2::len_sq`/`normalized` in `fire_hantavirus` are the same calls the
  file already makes.
- Import changes worth a look when it breaks: `weapons_wave3a.rs` now imports `TileKind`, `Sfx`,
  `SfxQueue`, `Player`, `Dropping` and the five `DROPPING_*` constants; `weapons.rs` imports
  nothing new (fully-qualified paths).
- The plate cue writes `world.player.face` and `Enemy::pos` between ticks (both are `pub`), which
  the scene module already does elsewhere (`pipe_lap_cue`, `hole_lap_cue`).
